# 远期目标：SPICE 仿真功能

## 背景

当前工具已经能导入 Multisim 网表和交叉引用报告，并在洞洞板上进行元件放置、底面布线和 DRC 检查。后续可以增加仿真能力，让用户在同一个工具里完成基础电路验证，减少在 Multisim、KiCad 或其它 SPICE 工具之间切换。

这个目标属于远期目标。短期仍优先保证导入解析、元件放置、布线、DRC 和 3D/2D 交互准确。

## 推荐选择

首选仿真内核：ngspice。

理由：

- ngspice 是成熟的开源 SPICE 仿真器，适合常见模拟电路的 DC、AC、瞬态等基础仿真。
- KiCad 的图形化 SPICE 仿真也集成 ngspice，说明它适合作为桌面 EDA 工具内嵌仿真后端。
- ngspice 官方支持编译为 shared library，也支持由外部程序控制仿真、读取结果、停止仿真、修改参数后继续运行。
- Qucs-S 文档在不确定选择哪个仿真后端时也推荐 ngspice。
- 生态中已有 Python、C/C++、Rust、Go 等接口经验，后续集成路径比较清晰。

备选仿真内核：Xyce。

适用场景：

- 后续需要更大规模电路、更强数值性能或并行仿真能力。
- 需要 Xyce 的高级分析能力，例如 harmonic balance、sensitivity、uncertainty propagation 等。

暂不推荐作为第一阶段主引擎，原因是集成复杂度和部署体积通常会高于 ngspice。Xyce 更适合作为第二阶段“高级仿真后端”。

不建议第一阶段采用纯前端 WASM 版 ngspice 作为主路径。WASM 方案便于浏览器端演示，但目前更适合作为实验路线；主功能应先采用本地 CLI 或后端进程调用，减少跨平台、文件系统、模型加载和调试复杂度。

## 分阶段路线

### 阶段 1：CLI 子进程集成

目标是先跑通最小可用闭环。

- 从当前工程数据生成 SPICE netlist。
- 调用本机安装的 `ngspice` 命令行执行仿真。
- 支持 `.op`、`.dc`、`.ac`、`.tran` 四类基础分析。
- 解析输出结果，返回节点电压、电流、波形数据和错误信息。
- 在 UI 中显示仿真日志、结果表格和基础曲线。

优点：

- 实现最快。
- 易于调试，用户也能直接复制 netlist 到 ngspice 复现。
- 不需要一开始处理 native shared library 绑定。

缺点：

- 需要用户安装 ngspice，或者我们随应用打包。
- 与仿真进程交互粒度较粗。

### 阶段 2：shared library 集成

当 CLI 跑通后，再考虑 shared library。

- Windows 使用 `ngspice.dll`。
- Linux 使用 `libngspice.so`。
- macOS 使用对应动态库。
- 通过 native binding 或后端服务封装统一接口。

优点：

- 可以更细粒度控制仿真。
- 可通过回调实时读取数据。
- 适合后续交互式探针、实时参数调整、停止/继续仿真。

风险：

- 跨平台动态库部署复杂。
- Node/native binding 增加构建和发布成本。
- 需要隔离仿真崩溃，避免影响主应用。

### 阶段 3：高级后端

在 ngspice 功能稳定后，评估 Xyce。

- 将仿真请求抽象为统一接口。
- 支持按工程或用户设置选择 `ngspice` / `xyce`。
- 保持 netlist 生成层可适配不同 SPICE 方言。

## 关键设计

### 数据模型

需要新增仿真相关配置：

- 仿真类型：Operating Point、DC Sweep、AC Sweep、Transient。
- 信号源定义：电压源、电流源、脉冲源、正弦源、小信号 AC 源。
- 测量点：节点电压、器件电流、差分电压。
- 模型库：`.model`、`.subckt`、`.include` 文件。
- 初始条件和仿真选项：`.ic`、`.options`。

### Netlist 生成

当前 Multisim 导入数据主要提供连接关系，不一定包含可直接仿真的 SPICE 模型。需要做一层映射：

- 电阻、电容、电感可直接生成 `R`、`C`、`L`。
- 二极管、三极管、运放、IC 需要模型库或内置简化模型。
- 电源、信号源、地节点需要用户显式定义。
- 所有仿真必须保证存在 SPICE 地节点 `0`。

### UI 交互

建议新增“仿真”面板：

- 分析类型选择。
- 起止频率、步进、瞬态时间等参数输入。
- 信号源和测量点列表。
- 运行、停止、清空结果。
- 日志输出。
- 曲线图和表格结果。

3D/2D 视图联动：

- 点击某个引脚，可选择将其加入测量点。
- 点击某个网络，可加入节点电压探针。
- 仿真结果曲线可以回链到对应网络。

## 第一阶段验收标准

- 能对一个只包含 R/C/L/电压源的简单电路生成合法 ngspice netlist。
- 能运行 `.op` 并显示节点电压。
- 能运行 `.tran` 并显示至少一条电压波形。
- ngspice 错误信息能原样显示给用户。
- 生成的 netlist 可导出，用户能用外部 ngspice 复现。

## 风险

- 导入报告中的元件值不一定能直接转换为 SPICE 数值，例如 `10kΩ`、`100uF`、厂商自定义命名等，需要规范化。
- Multisim 元件和 ngspice 模型之间不一定一一对应。
- 运放、比较器、开关电源芯片等复杂器件需要模型库，否则只能做连接检查或简化仿真。
- 没有地节点 `0` 时仿真无法可靠运行，需要 UI 强制用户指定 GND 网络。
- SPICE 方言差异会导致第三方模型兼容性问题。

## 仅有网表和交叉引用报告时的具体实施方法

### 输入边界

当前用户输入只有两类文件：

- 网表报告：提供网络名，以及每个网络连接了哪些 `元件.引脚`。
- 交叉引用报告：提供逻辑元件、物理元件、引脚编号和封装/类别等映射信息。

这两类输入足够建立连接图，但不足以直接完成完整 SPICE 仿真。缺失信息包括：

- 哪个网络是 SPICE 地节点 `0`。
- 电源和信号源的类型、幅值、频率、波形。
- 复杂器件的 SPICE `.model` 或 `.subckt`。
- Multisim 元件引脚顺序到 SPICE 模型引脚顺序的映射。
- 仿真类型和参数，例如 `.op`、`.tran`、`.ac`、`.dc`。

因此第一版不能假设“导入报告后自动仿真所有电路”。正确做法是：自动生成能确定的部分，并让用户补齐仿真必需信息。

### 数据转换流程

1. 使用现有导入解析逻辑生成结构化数据：
   - `ImportState.components`
   - `ImportState.nets`
   - 交叉引用解析后的物理引脚信息

2. 将每个网络转换为 SPICE 节点名：
   - 用户指定的 GND 网络固定映射为 `0`。
   - 其它网络做安全命名，例如 `N001`、`NET_OUT`、`VCC`。
   - 保留原始网络名到 SPICE 节点名的映射，方便 UI 回显和结果定位。

3. 将元件转换为 SPICE 元件行：
   - `R`：生成 `Rxxx nodeA nodeB value`。
   - `C`：生成 `Cxxx nodeA nodeB value`。
   - `L`：生成 `Lxxx nodeA nodeB value`。
   - `D`：需要模型名，默认可使用简单二极管模型。
   - `Q`：需要 NPN/PNP 模型名和 C/B/E 引脚顺序。
   - `U`、运放、比较器、芯片：必须有 `.subckt` 和 pin map，否则标记为“不可仿真/缺模型”。

4. 生成用户定义的激励源：
   - 电压源：`V1 VCC 0 DC 9`
   - 电流源：`I1 nodeA 0 DC 1m`
   - 正弦源：`Vsig IN 0 SIN(0 1 1k)`
   - 脉冲源：`Vpulse IN 0 PULSE(...)`
   - AC 小信号源：`Vin IN 0 AC 1`

5. 生成仿真指令：
   - 工作点：`.op`
   - 瞬态：`.tran step stop`
   - 交流：`.ac dec points start stop`
   - 直流扫描：`.dc source start stop step`

6. 写出完整 netlist，并保留导出入口：

```spice
* generated by perfboard autoroute

V1 VCC 0 DC 9
R1 VCC OUT 10k
R2 OUT 0 10k
C1 OUT 0 100n

.op

.control
run
print v(out)
.endc

.end
```

7. 调用 ngspice CLI：

```bash
ngspice -b generated.cir
```

8. 解析结果并回写到 UI：
   - 日志输出。
   - 错误和警告。
   - 节点电压表。
   - 后续支持波形曲线。

### 第一版 UI 设计

新增“仿真”面板，第一版只做最小闭环：

- GND 网络选择器：必须指定一个网络作为 `0`。
- 电源/信号源列表：用户手动添加激励源。
- 可仿真元件列表：显示哪些元件已能生成 SPICE 行。
- 缺模型元件列表：显示哪些元件因为没有模型暂时不能仿真。
- 分析类型选择：先支持 `.op`，再扩展 `.tran`。
- 运行按钮：生成 netlist，调用 ngspice，显示结果。
- 导出 netlist 按钮：方便用户外部复现。

### 第一版验收电路

优先用简单电路验收，不先碰复杂 IC：

- 电阻分压：`VCC -> R1 -> OUT -> R2 -> GND`，验证 `.op` 输出 `OUT` 电压。
- RC 低通：`Vin -> R -> OUT -> C -> GND`，验证 `.tran` 或 `.ac`。
- RLC 简单网络：验证基本无源元件生成。

### 模型映射策略

第一版建立一个模型映射表，按 `ref`、`category`、`packageName`、`value` 匹配：

```ts
interface SpiceModelBinding {
  ref: string;
  spiceType: "primitive" | "model" | "subckt" | "unsupported";
  modelName?: string;
  includePath?: string;
  pinMap?: Record<string, string>;
}
```

示例：

```ts
{
  ref: "U1",
  spiceType: "subckt",
  modelName: "TL062",
  includePath: "models/TL062.lib",
  pinMap: {
    "1": "OUT_A",
    "2": "IN-_A",
    "3": "IN+_A",
    "4": "VCC-",
    "8": "VCC+"
  }
}
```

没有绑定模型的复杂器件不参与仿真，UI 应清楚提示“缺少 SPICE 模型”，而不是生成错误 netlist。

### 实施优先级

1. 先实现 netlist 生成器，只支持 R/C/L 和用户定义电压源。
2. 支持 `.op`，输出节点电压。
3. 支持导出生成的 `.cir` 文件。
4. 支持 `.tran` 和基础波形显示。
5. 加入二极管、三极管默认模型。
6. 加入 `.include` 和 `.subckt` 管理。
7. 再考虑 shared library 和交互式探针。
