# 项目理解记录

记录时间：2026-05-22

## 用户确认的核心理解

1. 项目的核心问题是洞洞板自动布线，包括反面走锡路径和跳线方案。目标是让学生或使用者能够根据自动布线结果直接焊接洞洞板，而不是只做一个视觉上类似 EDA 的工具。

2. 一期主入口不依赖直接解析 `.ms14`。Multisim 支持分开导出 BOM 和网表，因此项目可以优先采用“网表 + 元件选型/BOM”的输入方式。

3. 网表和元件选型必须联合阅读。网表负责连接关系，选型/BOM 负责真实器件、封装、数量、多通道芯片等焊接必要信息。

4. U1A、U1B 在原理图逻辑上是两个比较器单元，但实际型号经常是一颗双通道芯片，例如 LM393。布线和布局时必须把它们映射到同一个物理封装，否则会生成错误的洞洞板布局。

5. 器件库不应只覆盖少量演示元件。长期目标是尽量覆盖 Multisim 中模拟电路常见的主要元件和芯片，尤其是常用直插器件、模拟 IC、比较器、运放、定时器、三极管、二极管、LED、电阻、电容、排针和接口类器件。

6. 项目不是短期课程项目，不按“时间不够就砍功能”的思路设计。架构和目录应尽量模块化、规范化，面向长期演进。

7. 洞洞板/万能板天然可以抽象为格点图。孔位是节点，相邻孔位之间可走锡或裸铜线的关系是边，已占用孔、已有线路、板边界和不同网络占用区域是布线约束。

8. 自动布线应先尽力完成底面走锡。如果格点搜索和重试策略仍无法完成某条网络连接，再采用跳线。跳线是 fallback，不是首选路径。

9. 短路、漏连等规则检查可以后期加强，甚至未来结合仿真能力。目前首要目标是根据给定网表和选型生成布局、走锡和跳线方案。

10. 3D 展示是核心功能，不是附属展示。系统需要生成 m x n 格点洞洞板，在正面放置可调整的 3D 元件，在反面生成走锡和跳线，并提供透视模式帮助用户检查布线结果。

11. 最终形态倾向于 EXE 桌面应用。但 Web + Python 的架构也可接受，尤其适合先构建 3D 前端、Python 解析和算法后端，再通过桌面壳封装。

12. 项目目录必须模块化、规范化，并为远期发展预留空间。导入器、Circuit IR、器件库、封装库、布局、布线、3D 渲染、桌面封装、示例和文档都应分层。

13. 后续不需要继续用苏格拉底提问法确认基础方向。当前理解已经足够建立项目结构，之后的问题应围绕具体技术决策、数据格式和算法细节展开。

14. 3D 元器件不需要追求具体型号的真实外观模型。项目只需要总体模型和封装大类模型，例如电阻、电感、电容、二极管、LED、TO-92、DIP-8、DIP-14、DIP-16、排针等。芯片型号负责提供引脚数、封装类别和引脚功能映射，3D 渲染只根据封装大类参数化生成外观。

## 当前架构决策

采用长期扩展优先的模块化结构：

- 输入入口以 `BOM/选型 + netlist` 为主。
- `.ms14` 直接导入作为后续增强能力，不作为主路径阻塞项目。
- 后端优先承担解析、器件映射、布局、布线和检查。
- 前端优先承担 3D 交互、透视检查、人工调整和导出预览。
- 桌面 EXE 作为最终交付形态保留独立目录。
- 3D 模型策略采用“封装大类参数化模型优先”，不依赖具体型号的第三方真实模型库。

## 后续需要细化的问题

- 网表输入格式优先支持 SPICE `.cir/.txt` 还是 Multisim Netlist Report `.csv/.txt`。
- 器件选型数据由 BOM 自动解析、用户手动选择，还是二者结合。
- 第一批器件库的最小可用清单。
- 走线算法是否从 A*/Lee + 多端点连接开始，还是直接设计 rip-up and reroute。
- 3D 前端选择 React + Three.js、Vue + Three.js，还是原生 Three.js。
- 桌面封装选择 Electron 还是 Tauri。
